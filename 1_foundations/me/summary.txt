First Project: Migration of Pepper Bank to Leumi’s Core Systems
The first project was the migration of Pepper Bank from working with its own independent core system to working with Leumi Bank’s core systems.
In practice, all Pepper’s data was migrated into Leumi’s databases, only with Pepper’s branding.
It was a huge project across the entire bank, but especially for us, since we were responsible for developing a new application and building a BFF (Backend for Frontend) server that fetches data via complex flows from the core systems.
Together with our group manager, I managed the complex tasks under tough deadlines.
We had to take an AWS training course to quickly learn how to use the AWS resources required for developing the BFF:
Lambda, AppSync, S3, DynamoDB, RDS, CDK, Secrets Manager
And more
For the data logic and organization in the format needed by the client, we used Lambdas written in NodeJS
(The APIs were exposed to the client through AppSync, which is AWS’s GraphQL product, and not the regular REST API
Looking back, we regretted this choice, but by then it was too late to change course due to deadlines. The regret came from the fact that GraphQL’s schemas are not strong enough.
We worked with DCS (Digital Core Services), which uses OpenAPI (Swagger) validations—very strict schema validations. GraphQL lacks such strong schema validations, which causes gaps and bugs.
Another issue was that GraphQL allows data aggregation (for example, fetching a list of savings accounts along with details for each in one request), giving the client control to decide what data to request.
While this reduces traffic in theory, in practice the disadvantages outweighed the advantages for our project. Unfortunately, it was too late to switch.)

Some integrations went smoothly with responsive partners, others required chasing people, escalating to project managers, and pushing hard.
Still, my persistence and initiative ensured successful integrations.

And more


Homepage Development
I was responsible for developing the homepage.
Product’s requirement was a homepage built of widgets, giving customers control over their data.
Widgets included credit cards, savings, recent transactions, and aggregations of similar transactions.
I took full ownership of this development.
I did a POC to choose the right database. DynamoDB was ideal, but security restrictions (later relaxed) forced us to use a GATEWAY for data processing and encryption/decryption. Leumi’s encryption vendor didn’t support DynamoDB, so I ultimately chose MySQL on RDS. (Mysql is a known DB. RDS is seating on the cloud, Mysql was more familiar than postgres)
I did a POC for ORM(Object-Relational Mapper) and decided to use Sequelize for its popularity and ease of use.
I built a shared code layer with a generic class for database access via Sequelize, created the tables, and implemented customer widget management (create, update, delete).
I also built the Lambdas that use this class.
For non-sensitive data, we used DynamoDB—for example:
* Basic customer indicators
* Bank list
* Institution list
* Large mappings between Leumi data and Pepper data (frequently updated, unsuitable for hardcoding)



Institution List Challenge
The institution list was large, and loading it took a long time. I didnt like it because it was a bad UX. So I went to the product to raise this issue. After I got their acceptance and blessings I started to research what is the best way to implement online search rather than fetching the full list to search locally on the client, since that took too long.
Initially, we couldn’t implement it due to lack of time. Later, I led a brainstorm with all relevant stakeholders (architects, etc.) to solve it.
We considered S3-based solutions and in-memory caching with efficient querying.
In the end, we decided that the DCS layer would handle caching and searching, while we just sent queries.
The leadership and initiative—from the initial unmet requirement to a fully working solution—was mine.




Two Microservices I Built Myself
Both in Node.js with Express:
1. Proxy Service:
    * When DCS didn’t expose certain data, we had to connect directly to the vendor's system.  In General DCS is our layer of data from pure LEUMI CORE SYSTEMS.
In some cases when its not pure core system like open banking for example, 
The decision was to work in front of the core systems by our selves.
    * I built a proxy microservice in the DCS layer using http-proxy-middleware.
    * The proxy rewrote base URLs and forwarded calls, handling required logic with minimal code.
2. On-Prem Microservice:
    * Part of a two-service architecture. One consumed Kafka events and wrote them to MongoDB.
    * The second (which I built) fetched data from MongoDB using Mongoose and exposed APIs via Express Router.

Reducing Duplicate Calls in the New App
We agreed not to repeat past mistakes with duplicate backend calls.
Homepage would fetch most relevant data, and inner pages should reuse it.
But under stress, client developers sometimes ignored this.
I tracked all duplicate calls, documented them, and posted a detailed message to management.
This led to a cross-team meeting where each lead was tasked to fix their team’s duplicates—initiated thanks to my report.

Joint & Multi-Account Support
Last year, we added joint/multi-account support.
* A field in user data indicated account type (personal or joint).
* This came from the Onboarding system.
* We also maintained a DynamoDB table for each user’s preferred account (present and future).
During one production issue, I led analysis sessions and discovered that the Onboarding system was sending invalid values not in the enum, causing missing fallbacks.
In addition i took the responsibility to fix the user data my self call in a way there will always be fallback. When there is a problem -> take the personal account as fallback.



User Data Redesign
Due to the rushed migration project, user data was poorly designed.
We were 4 developers teams working on the the same code and not always everyone made the best choices, which led to the followings:
Each customer had multiple IDs—account number, customer ID, user ID, etc. With joint/multi-accounts, it became messy, and the schema returned to clients was confusing and risky.
For the new app (also under tight deadlines), I insisted on redesigning user data to provide a single source of truth for identifiers, ensuring client developers couldn’t make mistakes.
